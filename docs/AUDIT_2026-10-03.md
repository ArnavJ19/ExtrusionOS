# ExtrusionOS business logic, access, and visibility audit

Date: 2026-10-03 (Asia/Calcutta)

Decision: **NO-GO for deploying this checkout against its configured hosted database.** There are six high-priority findings and six medium-priority findings. Existing automated checks pass, but targeted audit reproductions expose gaps outside that coverage. No application fixes or migrations were applied in this audit.

## Evidence and scope

Reviewed authentication/session resolution, route and action permissions, core RLS migration history, dealer ownership, order commercial visibility, configurator costing/quote/reservation flows, dispatch reservation consumption, invoice PDF dependencies, search/pagination, and relevant storage/RPC protections. Used the repository graph for discovery, then current source and SQL for evidence. This is a risk-focused deep audit, not an assertion that every route and every possible workflow is defect-free.

Evidence labels:

- **HOSTED READ-ONLY:** Current configured database API schema and zero-row queries, plus anonymous HEAD requests. No business records were downloaded and no remote mutations were made.
- **LOCAL SQL REPRODUCED:** Actual source policy statements or actual functions/triggers exercised in isolated PGlite with synthetic data. This is not a complete Supabase migration replay, hosted JWT test, or independent-session concurrency test.
- **LOCAL CODE REPRODUCED:** Actual permission/calculation functions or the actual action orchestration with a mocked database boundary.
- **SOURCE CONFIRMED:** Current implementation shows the defect; authenticated browser reproduction remains outstanding.

The Supabase management connector returned `UNAUTHORIZED` and requires reauthentication. Existing local application credentials were used only for GET schema/zero-row checks. Service-role schema access does not validate user-level RLS. No credentials are included in this report or the reproduction script.

## High-priority findings

### A00 - P1 - Hosted database does not satisfy this checkout's schema contract

**Evidence: HOSTED READ-ONLY plus SOURCE CONFIRMED.** The configured project's REST schema returned HTTP 200 but did not advertise `save_system_configuration_atomic` or `submit_dealer_receipt_atomic`. It did advertise `save_order_atomic` and `save_ready_dispatch_atomic`. Invoice snapshot columns were absent from the API schema. A direct zero-row GET selecting `invoices.supplier_snapshot` returned HTTP 400, SQLSTATE `42703`: `column invoices.supplier_snapshot does not exist`.

`app/api/pdf/invoice/[id]/route.ts:16` selects both snapshot columns. Its line 19 maps any invoice query error to HTTP 404, so a schema deployment problem appears as "Invoice not found." Configurator saving/recalculation calls the missing RPC at `lib/systems-configurator/actions.ts:213` and `:368`; dealer receipt submission calls its missing RPC at `lib/enterprise/dealer-workflows.ts:36`.

**Impact:** This checkout's invoice PDF query is incompatible with the configured database. Configurator/receipt RPC availability is also inconsistent with the source. The deployed application's version was not established, so this is not a claim that all current deployed screens fail.

**Remediation:** Compare the hosted migration ledger with the checkout, rehearse prerequisite migrations and data preflight in isolated staging, then deploy schema and application together. Do not apply only the latest migration blindly: A03 must be resolved first. Treat missing API RPCs as an availability finding until catalog/privilege inspection establishes whether they are absent or unexposed.

### A01 - P1 - Core reads no longer enforce dealer isolation

**Evidence: LOCAL SQL REPRODUCED.** `0042_dealer_quote_order_isolation.sql:34` originally scopes quotes to the user's dealer. Later, `20260512_phase1_rls_fixes.sql:69` replaces that read policy with company-only access. The same migration introduces company-only customer, quote-line, and order reads at lines 27, 83, and 101. `20260602000000_pcda_phase1_completion.sql:100` gives `order_items` company-only `FOR ALL` access. The narrower quote-line policy survives under a different name, but permissive policies are ORed together.

The audit script replays 60 literal core policy create/drop statements in filename order on five fixture tables. An authenticated dealer-A identity reads synthetic dealer-B rows from `customers`, `quotes`, `quote_items`, `orders`, and `order_items`. The other company's fixture rows remain hidden. No later literal policy replacement or relevant dynamic cleanup was found for these five tables.

**Impact:** Same-company dealer/customer confidentiality can be bypassed through direct database API queries, regardless of page filters. Quotes and their lines also contain commercial/internal fields. This is a same-company ownership failure; cross-company disclosure was not reproduced.

**Remediation:** Replace the complete effective policy set with explicit internal-role and dealer-ownership branches. Define customer visibility for dealers through owned relationships. Test sibling dealers and separate companies using authenticated sessions and actual field projections.

### A02 - P1 - Read-only roles retain core-table write authorization at RLS

**Evidence: LOCAL SQL REPRODUCED.** `20260512_phase1_rls_fixes.sql:31`, `:73`, `:87`, and `:105` authorize core inserts by company alone; associated update policies do the same. Quote-line deletion at line 96 is company-only. `20260602000000_pcda_phase1_completion.sql:100` authorizes all order-line operations for the company.

In the policy fixture, a viewer updates rows in all five core tables and deletes an order line. The fixture deliberately isolates authorization: the full business trigger stack is not installed, so this does not claim every possible hosted mutation succeeds. The policy layer itself does not enforce the application role restrictions.

**Impact:** Hiding edit buttons and guarding server actions cannot secure browser-accessible tables with these effective policies. Customer-master edits, line edits/deletes, and resulting financial/workflow changes require database-level role checks.

**Remediation:** Restrict direct writes by role and ownership, and make sensitive workflows RPC-only where appropriate. Add negative tests for viewer, production, dealer, and suspended users against the full schema, including permitted-column changes and line deletion.

### A03 - P1 - New reservation guard blocks legitimate dispatch consumption

**Evidence: LOCAL SQL REPRODUCED using the actual consumption function and capacity trigger.** `20260721091307_physical_dispatch_stock_provenance.sql:351` reduces a stock batch before line 356 marks the reservation consumed. `20260930000000_astra_audit_fixes.sql:184` checks that remaining stock still covers all active reservations and forbids an unavailable stock status while any reservation is active.

Synthetic reproduction: 100 kg stock, one active 100 kg reservation, one 100 kg dispatch packing line. Calling `private.consume_dispatch_reservations` raises `Release or consume active reservations before changing reserved stock`. The statement rolls back, leaving no consumption row. Smaller reservations can also fail when the new balance is below the still-active total.

**Impact:** The existing passing reservation tests do not cover integration with dispatch. Applying the latest guard can block valid reserved-stock dispatches.

**Remediation:** Coordinate reservation consumption and stock reduction in one locked transaction, with a consistent lock order and invariants based on remaining reservations. Test full and partial consumption, multiple reservations, retries, rollback, and concurrent operations together.

### A04 - P1 - Shared order database exposes values hidden by the detail page

**Evidence: LOCAL CODE REPRODUCED and SOURCE CONFIRMED.** `app/(dashboard)/orders/[id]/page.tsx:52` derives `canSeeValue` from quote-read permission and suppresses commercial values for production users. However, `components/modules/operations/module-config.ts:82` selects all order fields, line 107 always includes `Order Value`, and `module-database-client.tsx:110` maps every configured column without a role filter. `/orders/database` allows production and other operational order-read roles.

**Impact:** A production user can navigate from a financially restricted detail page to an unrestricted database table. Commercial data is also fetched into the browser. This contradicts the role-specific dashboard's commercial visibility rule.

**Remediation:** Use a single field-level visibility contract across overview, database, detail, export, and API access. Apply an authorized projection before sending data to the browser; hiding a column alone is insufficient.

### A05 - P1 - Configurator material amounts bypass the internal-cost restriction

**Evidence: SOURCE CONFIRMED.** `app/(dashboard)/systems-configurator/projects/[id]/quote/page.tsx:24` permits internal costing only for owner/admin/accounts. Nevertheless, line 61 renders every `system_material_summary.amount` for all users who can read the configurator, including production and sales. Those amounts are persisted from costing inputs at `lib/systems-configurator/actions.ts:364`; glass/hardware amounts feed internal cost in `costing-engine.ts:74` and `:76`.

The latest `astra_read` policy at `20260930000000_astra_audit_fixes.sql:37` also authorizes operational users to read the complete `system_configurations` and material-summary rows, including `internal_cost`, margins, and rates. No column-level restriction or separate safe projection was found.

**Impact:** "Internal Cost - Restricted by role" does not protect the underlying data or material-cost amounts. This finding concerns restricted internal users, not a demonstrated public/customer-portal leak.

**Remediation:** Separate operational quantities from commercial/cost data at the database/API boundary and consistently gate all cost-bearing UI fields and reports.

## Medium-priority findings

### A06 - P2 - Configuration-to-quote creation is not atomic or idempotent

**Evidence: LOCAL CODE REPRODUCED.** `generateSystemQuote` issues independent writes: quote header at `lib/systems-configurator/actions.ts:580`, item at `:588`, then configuration link at `:633`. It checks `configuration.quote_id` only before writing and does not lock the configuration during conversion.

The reproduction script extracts and runs the actual action orchestration with a mocked database adapter. An injected item-insert failure leaves the header inserted. A failure linking the configuration can similarly leave a complete unlinked quote. Concurrent calls can both pass the initial check and create separate quotes; that concurrency case is inferred from the sequence, not independently reproduced.

**Remediation:** One authorized, idempotent conversion RPC should lock the configuration, create header/items, and set the link atomically. Test injected failure at each write and concurrent retries. Centralized quote numbering does not make these three writes atomic.

### A07 - P2 - Costing profit percentage ignores discounts

**Evidence: LOCAL CODE REPRODUCED.** `lib/systems-configurator/costing-engine.ts:111` reports `marginAmount / internalCost`, although the selling subtotal subtracts `discountAmount` at line 86. Actual function example: cost 100, markup 20%, discount 30 -> selling subtotal 90, but `profitPercent` remains positive 20% despite a loss of 10.

**Impact:** The returned calculation contract misstates profit. No current UI consumer of this specific `profitPercent` field was found; generated quote profit is recalculated separately, so this is not evidence that every quote displays the wrong profit.

**Remediation:** Calculate realized profit after discounts and name the denominator explicitly (sales margin versus cost markup). Test break-even, losses, and discounts exceeding the marked-up price.

### A08 - P2 - Accounts cannot reach explicitly accounts-enabled costing

**Evidence: LOCAL CODE REPRODUCED and SOURCE CONFIRMED.** The costing page and PDF handler explicitly allow accounts for internal cost, but `can('accounts','read','systems_configurator')` and route access both return false. The latest `astra_read` role list also omits accounts.

References: `lib/auth/permissions.ts:132`, `lib/auth/route-permissions.ts:88`, `lib/systems-configurator/access.ts:5`, `app/api/pdf/systems-configurator/[id]/[type]/route.ts:21`, `20260930000000_astra_audit_fixes.sql:37`.

**Impact:** Accounts has an advertised report capability without the page or underlying data access required to use it. Directly reaching the PDF URL does not overcome the RLS exclusion.

**Remediation:** Resolve the intended accounts capability and align route, action, report, and database rules. Grant only the approved costing/read scope.

### A09 - P2 - Production manager's Reserve Stock button fails its action gate

**Evidence: LOCAL CODE REPRODUCED and SOURCE CONFIRMED.** The BOM page at `app/(dashboard)/systems-configurator/projects/[id]/bom/page.tsx:76` shows the reservation button for inventory-update or production-update roles. Production manager passes that check and can read the configurator. However, `reserveSystemBomProfileStock` at `lib/systems-configurator/actions.ts:643` requires configurator **update**, which production manager does not have.

The latest reservation RLS explicitly allows production/factory/inventory managers, while configurator update permits owner/admin/sales manager. Sales manager can enter the action but cannot insert reservations under that policy. Across these two gates only owner/admin can complete this path.

**Remediation:** Authorize reservation actions using the intended inventory/reservation capability; use the same rule for the button, server action, and database. Do not grant broad configurator editing merely to enable stock reservation.

### A10 - P2 - Customer GST search breaks pagination; relation search silently truncates matches

**Evidence: SOURCE CONFIRMED.** `components/modules/operations/module-database-client.tsx:81` loads a normal ten-row page, then lines 86-94 fetch up to ten GST matches without an offset and merge them into that page. The displayed result can exceed ten rows, repeat GST matches on later pages, and undercount more than ten GST-only matches. GST matches also bypass the requested sorting.

At lines 54-56, customer/profile/order relation lookup IDs are capped at 50 before the main query. Records linked to later matching entities cannot appear in a broad search even when the user pages through results.

**Remediation:** Perform all search predicates in one server-side query/RPC with a single count, stable sort, and range. Test more than one page of GST-only matches and more than 50 related entities.

### A11 - P2 - Saved project list silently hides older records and database failures

**Evidence: SOURCE CONFIRMED.** `app/(dashboard)/systems-configurator/projects/page.tsx:13` ignores the query error and limits records to the newest 100 at line 18. The page has no next page or search. Line 44 treats any missing data as "No configurations yet."

**Impact:** The 101st and older saved projects cannot be discovered from this list. A failed query or incompatible schema can be presented as an empty business dataset, obscuring the actual problem.

**Remediation:** Implement the required ten-row server pagination, search/filter/sort, and explicit error state. Test the 101st record and a rejected query.
